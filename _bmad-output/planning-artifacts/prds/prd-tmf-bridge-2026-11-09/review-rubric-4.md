# PRD Quality Review — TMF-Bridge (post 2026-11-20 amendments)

## Overall verdict
The PRD still has a sharp thesis (TMF API from configuration, validated at runtime, built to be retired). Its requirements are specific, and it records decisions with rejected alternatives. The 2026-11-20 amendments are mostly coherent. Two new defects came with them. The id-map transform has no defined behaviour when an entry is missing. FR-17's "added only when new / clash rejects" rule makes re-importing a whole export into the same runtime fail, because backends have no identical-skip rule. Beyond those, the amended FRs have become dense, multi-clause requirements with some undefined edges (filter semantics, overhead measurement, credential-in-URL detection, glossary path syntax). The architecture-amendment rationale is only partly recorded in the addendum.

## Decision-readiness — adequate
Decisions are stated as decisions and the addendum records rejected alternatives for most of them: import replace versus skip, per-mapping export without entries, exports including drafts, backend decoupling. Trade-offs are named, for example "a backend edit changes live calls on their next call".

Weak spots:
- The status is `final`, yet open items live only in the addendum. Examples are "how a legitimate id-map merge or restore of a populated runtime is done, which S1 import does not cover" and "FR-29 per-sub-step applicability ... goes to architecture". Nothing in the PRD body flags them.
- The 2026-11-20 section of the addendum explains only map/filter, import-over-Draft and NFR-1. It says "Nine changes" but gives no rationale for the FR-16 URL-credential rule, FR-20, FR-22's exclusion wording, FR-32's autosave clause, FR-37's glossary, or FR-39's reverse-lookup clash. The 2026-11-16 addendum entry "clash means same resource and TMF id with a different backend id" is now superseded by FR-39's second clash type. It is not marked as such.

### Findings
- **low** Addendum not reconciled with amendments (addendum "2026-11-16 decisions" vs FR-39; "2026-11-20 architecture amendments") — The superseded clash definition remains, and six of the nine amended items have no recorded rationale. *Fix:* mark the 11-16 clash bullet superseded and add one line per remaining amendment.
- **low** Unsurfaced trade-off in FR-39 — "two different TMF ids of the same resource mapped to the same backend id" is rejected so reverse lookup has one answer. That blocks legitimate many-to-one cases (several TMF ids exposing one backend record). The cost is not named. *Fix:* state it as a decision with the given-up case.

## Substance over theater — strong
There is no persona theater: two named personas, Inès and Tomás, each drive decisions. The vision is specific and honest ("Polymorphism, version differences, task operations and hub semantics may still need code"). NFR-1 now has real thresholds and conditions. The dropped throughput and availability targets are called out rather than padded. Nothing reads as furniture. FR-30 and FR-12 do carry UI-copy detail that belongs to the UX spine (see Shape fit).

## Strategic coherence — strong
The thesis is stated, and S1 scope follows it: capability slices, two APIs as test beds, and a closed transform list and verdict rule set. Out of Scope and Later are consistent with that. Success Measures are the UJs, with "Numeric metrics are deferred" stated honestly.

### Findings
- **low** No counter-metric and a numeric tension (Success Measures; NFR-1; UJ-2) — Success is "each UJ runs end to end", with no guard such as accuracy or overhead regression. UJ-2/UJ-4 assert "under 100 ms" and "within the overhead budget" while Success Measures says numeric metrics are deferred. *Fix:* point UJ-2/UJ-4 at NFR-1 conditions explicitly, or note that NFR-1 is the one numeric commitment.

## Done-ness clarity — adequate
Most FRs have a verifiable consequence: FR-2 (501/404), FR-3, FR-31/33 (version and status), FR-39 (clash rules), FR-18 (identical state gives identical text). The amended requirements are where precision slips.

### Findings
- **high** Id-map transform with no matching entry is undefined (FR-5 "id-map (translate a TMF id to a backend id and back)"; FR-6; FR-39; FR-29 rule list; UJ-5) — Nothing says what happens on a lookup miss in either direction: pass through, 404, or a TMF Error with what status. FR-39 says entries are seeded or edited so "the transform of FR-5 has data to translate". UJ-5's "still returns 404: the id is not in that backend" cannot distinguish a backend miss from an id-map miss. FR-29's closed rule set checks "id-map transform present" but not "entry exists". Partners see this behaviour at runtime (FR-2/FR-4). *Fix:* add an FR-5/FR-6 consequence for the miss (status and TMF Error code, both directions). Add an "id-map entry found" check to the FR-29 closed list, or say explicitly that it is excluded.
- **medium** "map and filter over arrays" is under-specified (FR-5) — "filter" has no stated predicate source. The closed list has "conditional", but it is not said whether filter reuses it. FR-5 adds "The studio shows an array rule as a nested sub-table", yet FR-10 still defines the mapping as "a table (TMF field, transform, backend field)". FR-21 lineage, FR-30's "fields translated" tile and FR-29's "empty mapped fields" rule say nothing about array elements. No transform has a stated example or boundary, such as date or number formats or lookup-miss behaviour. *Fix:* give each transform one testable consequence, and say how arrays count in lineage, the tile and the empty-field rule.
- **medium** Overhead measurement is inconsistent between FR-20, FR-22 and NFR-1 (FR-22 "excluding the lineage capture of studio test calls (FR-21)"; FR-20; NFR-1 "lineage excluded") — FR-20 makes step results available on studio test calls, but only lineage capture is excluded. Step-result capture on those same calls is not. FR-29 and FR-30 then compare that value to the NFR-1 target. "Backend's own response time" is also not something a bridge can observe. It can only observe the round trip. *Fix:* exclude "step-result and lineage capture", and define backend time as the observed backend round trip.
- **medium** NFR-1 conditions are incomplete (NFR-1 "warm cache, single bridge instance, zero-latency mock backend, payload up to 50 KB"; FR-29) — "warm cache" names no cache anywhere in the PRD. p95 is given with no request rate or concurrency. FR-29 compares a single studio call to a p95 target measured under zero-latency mock conditions, so the "info note" will fire arbitrarily. *Fix:* name the cache, give the load profile (sequential or N concurrent), and say what a single-call comparison means.
- **medium** FR-32 conflict path has no way to "review their changes" (FR-32 message "Review their changes before you apply."; FR-31 "History, diff and rollback are Later") — The message tells the user to review, but no S1 capability exists to view the other person's changes. The same applies to a stale autosave: unsaved edits are kept, but the next action is undefined. *Fix:* state the S1 resolution (reload the latest and re-enter, or copy the unsaved edits out). Alternatively pull a minimal view of the current draft into S1.
- **medium** Constants and headers can carry credentials past FR-16 (FR-16 "never secret values or other credentials"; FR-5 "constant", "lookup table"; UJ-3 maps header inputs) — A constant transform can hold an API key or token, and it is exported in every mapping export (FR-15, FR-38). Only the URL-embedded credential case is covered. The promise is untestable as written. *Fix:* narrow FR-16 to what is checkable, or add a rule such as warning on constants mapped to credential-like header names.
- **medium** Several FRs are compound and not atomic (FR-17, FR-30, FR-34, FR-39) — Each carries 6 to 10 independently testable behaviours in a single paragraph. FR-17 holds atomicity, Draft landing, replace/skip, conflict refusal, additive backends, clash and identical-entry rules and version naming. This makes story extraction and test traceability hard. *Fix:* split into sub-IDs or bullet consequences (FR-17a to FR-17f, and so on).
- **low** FR-16 credential-in-URL rule has no detection definition (FR-16 "credentials embedded in the URL") — It is unclear whether it covers userinfo only (`user:pw@host`) or query-string tokens (`?api_key=`). FR-34 does not mention the save-time validation. *Fix:* define the pattern, and cross-reference it in FR-34.
- **low** FR-29 rule "unreachable or timed out" implies a timeout that no requirement defines (FR-29; FR-4 "transport faults"; Later "retry and timeout"). *Fix:* state the fixed S1 timeout value or default.
- **low** FR-13 does not say how "never change backend state" is enforced (FR-13; FR-5 "An operation binds to a mapping") — An analyst could bind a non-GET operation and run Test. *Fix:* restrict Test sub-step (c) to GET, or state the guard.
- **low** FR-25 reads as self-contradictory — "require an OIDC bearer token, whatever the access path. This is configurable." Pre-existing, but it is still untestable. *Fix:* state the configurable dimension.

## Scope honesty — adequate
Out of Scope is explicit and has no silent de-scoping: mocks only, no expression language, no certification claim. Later is itemized. The PRD has no inline `[ASSUMPTION]`, `[NOTE FOR PM]` or Open Questions, so open-items density is zero in the body even though the addendum carries real open items. The assumptions index round-trips trivially (nothing inline and no index). That is acceptable for the stakes, but it understates the open architecture items.

### Findings
- **high** Whole-configuration round trip fails on backends (FR-17 "Backends and id-map entries are added only when new. A clash with an existing backend name ... makes the file invalid and it is rejected"; FR-15 "imports back"; FR-38) — Id-map entries get an explicit "identical entry is skipped" rule. Backends do not. Re-importing an unchanged export into the same runtime is therefore rejected whenever it contains any backend. So is a per-mapping restore, and so is merging two environments that share a backend name. This weakens the FR-15 exit path and contradicts FR-17's own symmetry. *Fix:* add an identical-backend-is-skipped rule, with a clash only when the definition differs. Alternatively state that same-runtime re-import is unsupported.
- **medium** Import cannot create or overwrite a dependency a mapping needs (FR-17; FR-38 "names the backend it uses and carries no backend definition") — An imported mapping that names a backend absent in the target is not covered. FR-17 does not say whether it is an invalid-file problem, a Draft with a dangling reference, or a warning. *Fix:* state the rule in FR-17 and FR-38.
- **medium** Out of Scope claims FR-14 to FR-18, FR-38 and FR-39 are enough for an outer drift-correction process, but import now never touches Live (Out of Scope last bullet; FR-17 "Import never changes the live configuration"; addendum "how a legitimate id-map merge or restore of a populated runtime is done, which S1 import does not cover") — Import can only add Drafts and new backends and id-map entries. Correcting drift in backends, id-map entries or Live mappings must go through the configure/apply REST calls. The unsupported restore case is recorded only in the addendum. *Fix:* add an explicit Out of Scope or Later line for populated-runtime restore and merge. Say that drift correction uses configure/apply, not import.
- **low** FR-32 locking covers mapping apply and draft autosave only (FR-32; FR-34; FR-39) — Concurrent edits to a backend or id-map entry have no version or entity-tag check. With FR-36 (no roles), last-write-wins applies to live-affecting objects. *Fix:* state it as an S1 limitation, or extend FR-32.
- **low** Backend deletion guard is unclear for Drafts (FR-34 "cannot be deleted while mappings use it") — It is not said whether a mapping that has only a Draft, or a Live mapping's later Draft, counts. *Fix:* say "Live or Draft".

## Downstream usability — adequate
IDs are contiguous and unique: FR-1 to FR-39, NFR-1 to NFR-6 and UJ-1 to UJ-5. FR order is non-monotonic because FR-14, FR-15, FR-38, FR-39, FR-16, FR-17 and FR-18 sit in F5 and FR-28 to FR-35 and FR-37 sit in F4. Cross-references resolve. Every UJ has a named protagonist. The PRD has no Glossary section of its own. FR-37 lists glossary terms for the product manual, which is a different purpose.

### Findings
- **medium** Glossary path-syntax contradiction (FR-37 "field path (JSON Pointer)" vs FR-19 "field paths (for example `password`, `resource.secret.value`)") — FR-37, introduced in the amendment, standardises the manual's term as JSON Pointer (`/resource/secret/value`). FR-19, FR-30 (FR-19 sensitive field paths masked) and FR-23 use dotted names. Architecture and stories could implement either syntax. *Fix:* pick one syntax and state it in FR-19, or relabel FR-37.
- **medium** UJ-5 replay promise vs masking (UJ-5 "replays the call without asking her anything"; FR-30 "sample request and response with the FR-19 sensitive field paths masked"; "FR-23 redaction applies") — If the sample or the backend request body has sensitive values masked, copied curl and Postman cannot reproduce the call unless the placeholder scheme covers them. Only `$SECRET_VALUE` is defined, and it covers secrets, not masked field values. It is also unclear whether the bundle's "Exchange view record" is masked. *Fix:* say what masked fields look like in the replay artifacts and what the colleague must supply. Soften UJ-5 accordingly.
- **low** Glossary and term drift — FR-37's glossary list omits terms the PRD relies on: Draft, Live, Exchange view, share bundle, step result, bridge overhead and Connect picker. "Exchange view" (FR-30, UJ-1) and "exchange view" (FR-11) differ in case. FR-30 calls the overhead tile "bridge overhead, FR-22, shown as the exchange latency tile". "Latency" suggests total time and conflicts with FR-22's definition. "id map" (noun) and "id-map" (adjective or transform name) are used consistently but FR-5 uses "id-map" for the transform name. "mapping version", "version number" (FR-31) and "Version {n}" are used interchangeably. *Fix:* add a short PRD glossary and use one casing and name per concept.
- **low** "Configured" and "Configuring" are loose against Draft, Live and Apply (FR-2 "unconfigured operation returns 501"; FR-3 "Configuring a resource makes it answer"; FR-33 "A Draft is stored and never served") — A Draft-only operation is presumably 501, and "configuring" actually means Apply. Neither is stated. *Fix:* define "configured" as having a Live mapping.

## Shape fit — adequate
This is a chain-top, multi-role tool. The integrator is the day-one user, partners call the API, and tech colleagues receive bundles. A UJ-led PRD is appropriate. The PRD is over-specified at the UI layer for a requirements document. FR-12, FR-28, FR-29, FR-30 and FR-32 carry quoted UI strings, tile names, panel counts and step structure, and the UX spines and DESIGN/EXPERIENCE docs already own those. Duplication risks drift (see the tile naming and path-syntax issues). UJ-2 and UJ-4 are thin partner journeys but they do real work, since they carry the 501 and the overhead contract.

### Findings
- **low** UI copy and layout living in FRs (FR-12, FR-29, FR-30, FR-32) — Quoted strings such as "Version {n} is live" and "Checks passed. The output matches ..." and a fixed three-panel layout are requirements-level commitments that a UX redesign would have to amend the PRD to change. *Fix:* keep the behavioural consequence in the FR and point to the UX spine for wording.
